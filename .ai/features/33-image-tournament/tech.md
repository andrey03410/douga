# Технические решения

> Автономный режим до вливания: решения `T…` принимает агент
> ([brief.md](brief.md#разрешение-автономности)). Решение совпадает с рекомендацией,
> если не сказано иначе.

## Исходная система (по коду, 2026-11-07)

- **Движки** ([engines/index.ts](../../../src/lib/domain/engines/index.ts)). Интерфейс `Engine`
  с позиционными аргументами: `nextQuestion(items, log, k, bonus)`, `nextPair`, `isComplete`,
  `ranking`, `progress`, `partialRanking`. Движков три: `merge` (пары, бросает `NeedComparison`),
  `swiss` (сид — меньше соперников, потом очки), `round_robin` (жадная группа в порядке загрузки).
  Все чистые и переигрывают лог пар.
- **Ответ экрана** ([group-answer.ts](../../../src/lib/domain/group-answer.ts)).
  `decodeGroupAnswer(ranked, rest)` раскладывает экран в C(k,2) пар, `rest` — ничьи между собой.
  `plannedScreens(scheme, n, k)` — оценка для трёх схем.
- **Сервис** ([tournaments.ts](../../../src/server/tournaments.ts)).
  - `nextComparison` берёт схему турнира (`Tournament.scheme`), k турнира и бонус сегмента.
  - `recordGroupAnswer` под writer-lock перечитывает срез, сверяет экран и пишет `ComparisonBatch`
    с парами, пропуская уже известные.
  - `undoLastAnswer` снимает последний батч, `finalize` пишет `Ranking` всех треков
    сегмента, `reorderRanking` требует полный набор.
- **Сегменты** ([tournament-segments.ts](../../../src/server/tournament-segments.ts)).
  `updateTournamentSegments` принимает полный состав. Батчи с перенесёнными треками снимаются
  после `confirmReset`. Схема в `segmentProgress` — общая турнирная.
- **Данные** ([schema.prisma](../../../prisma/schema.prisma)).
  - `Track.kind` — `audio | video`.
  - `coverPath`/`coverArtId` — обложка, `artist` — второй ряд подписи.
  - `ComparisonBatch` без вида. `Ranking` уникален по `(tournamentId, trackId)`.
- **Импорт.** [upload.ts](../../../src/lib/upload.ts): `mediaKind` знает только аудио и видео,
  картинки архива пропускаются. Форма создания шлёт ZIP и `scheme`.
- **MCP** ([tournament-tools.ts](../../../src/mcp/tournament-tools.ts)). Четыре инструмента.
  `tournament_create` принимает `{path}|{assetId}` только audio/video, `scheme` по умолчанию `swiss`.
- **Shikimori** ([lib/shikimori.ts](../../../src/lib/shikimori.ts)).
  - `fetchFreshPosterUrls` — GraphQL пачками по 50, общая очередь.
  - Картинки — очередь `asset` с паузой 250 мс без минутного бюджета.
  - Живой GraphQL отдаёт у `characters` и `animes` поля `id`, `name`, `russian`, `url`,
    `poster.originalUrl`, у аниме ещё `kind`, `airedOn.year`, `studios.name`.
    Списка тайтлов у персонажа в GraphQL нет (проверено запросом 2026-11-07).
- **SDK** ([sources.ts](../../../src/server/studio/sources.ts)).
  - `reconcileSource` делает участника из `Ranking` топ-N.
  - `label = artist ? "artist — title" : title`, звук — у audio/video, визуал — у видео
    либо привязка `track` с `media:"cover"`, если есть `coverPath`/`coverArtId`.
  - `Participant` ([types.ts](../../../src/video/types.ts)) знает
    `label/caption/comment/album/score/bestMomentSec/rank/media`.
  - Привязка `track` разрешена в любом документе. Её владение проверяет `references`
    ([assets.ts](../../../src/server/studio/assets.ts)).
- **Зависимостей обработки картинок нет** (sharp не установлен). Есть `ffmpeg-static`.

## Решения

### T01. Участник-картинка — это `Track` вида `image`

- Варианты: (а) `Track.kind = "image"`, а файл картинки одновременно служит и обложкой
  (`coverPath = filePath`); (б) отдельная модель участника.
- Рекомендация: (а). Без новой работы продолжают работать:
  - миниатюра в результатах (`/api/tracks/:id/cover`);
  - замена из пула (`coverArtId`, `ImageChoice`) и возврат исходной (`coverArtId = null`);
  - привязка SDK `track` + `media:"cover"`;
  - защита удаления пула.

  `sizeBytes` считает файл один раз.
- **Решение:** (а). Набор расширений — `IMG_EXT` (jpg, jpeg, png, webp, gif).
  AVIF не берём: ffmpeg-static его не декодирует, а значит, не будет ни миниатюры,
  ни кадра SDK. Это отступление от P03, записано здесь.

### T02. Новые поля участника

- `Track.subtitle String?` — подзаголовок (P05). `artist` у картинки пуст, поэтому
  подпись SDK — просто имя.
- `Track.sourceUrl String?` — ссылка на Shikimori.
- `Track.sourceKey String?` — ключ повтора: `shikimori:character:<id>`, `shikimori:anime:<id>`,
  `art:<artId>`. Повтор внутри сегмента сервис отклоняет (`DUPLICATE_ITEM` с именем, P06).
  Ограничения в БД нет: перенос между сегментами легален.
- `Track.note String?` — основание агента (P05).
- `Track.excluded Boolean @default(false)` — исключение (P13).
- **Решение:** как выше. Все поля аддитивные: `db push` без потери данных.

### T03. Алгоритм у сегмента

- `TournamentSegment.scheme String?` и `schemeSettings String?` (JSON) хранят алгоритм сегмента.
- `Tournament.scheme` становится значением по умолчанию для новых сегментов.
  Новое поле `Tournament.schemeSettings String?` хранит его настройки.
- Новое поле `Tournament.schemePending Boolean @default(false)` означает «алгоритм ещё не выбран».
- `effectiveScheme(segment, tournament) = segment.scheme ?? (tournament.schemePending ? null : tournament.scheme)`.
  Старые сегменты наследуют схему турнира: миграция данных не нужна.
- Размер группы и слепой режим остаются турнирными (P16).
- `null` — «алгоритм не выбран»: `next` отдаёт `schemeRequired: true`, вопросов нет.
- **Решение:** как выше.

### T04. Общий вход движков (Engine v2)

- Варианты: (а) добавить новые методы рядом со старыми позиционными; (б) один объект входа
  и единый результат.
- Рекомендация: (б).
  - Новым алгоритмам нужны настройки, корзины и вид вопроса, позиционные аргументы
    это не вынесут.
  - Старые тесты движков переписываются механически на тот же вход. Их утверждения
    не меняются и служат регрессией: «существующие не сломаны».
- Форма:

  ```ts
  type Question =
    | { kind: "rank"; items: string[] }   // упорядочить группу
    | { kind: "pick"; items: string[] }   // выбрать одного лучшего
    | { kind: "tier"; item: string };     // положить в корзину
  interface EngineInput {
    items: string[];              // активные (не исключённые), в порядке загрузки
    comparisons: Comparison[];
    groupSize: number;            // уже ограниченный k
    bonusOpponents: number;
    settings: SchemeSettings;     // проверены схемой алгоритма
    tiers: Map<string, number>;   // последняя корзина участника (только tiers)
  }
  interface EngineResult {
    placed: RankedItem[];                                  // строгие места
    unplaced: { id: string; tier?: number; stage?: number }[]; // без мест
  }
  interface Engine {
    scheme; maxGroupSize; partial: boolean;
    next(input): Question | null;
    result(input): EngineResult;
    plannedScreens(n, k, settings): number;
  }
  ```

- Реестр `SCHEME_INFO` в домене: подпись, описание, настройки по умолчанию, zod-схема настроек.
  Его читают сайт (окно выбора, оценка экранов на клиенте), API и MCP.
- **Решение:** (б).

### T05. Лог ответов

- «Выбери лучшего» пишется парами «победитель > каждый», без ничьих между остальными (P18).
  `decodePickAnswer(winner, others)`.
- `ComparisonBatch.kind String @default("rank")` (`rank|pick|tier`), `ComparisonBatch.tier Int?`.
- Ответ корзины — батч `kind:"tier"` с `itemIds:[id]` и номером корзины без пар.
  Последний батч участника побеждает. Правка на доске — тоже новый батч, поэтому undo её откатывает.
- `tier = -1` — «не участвует»: в той же транзакции ставит `excluded = true`.
  Undo такого батча возвращает `excluded = false`.
- Undo по-прежнему снимает последний батч любого вида.
- **Решение:** как выше. Существующие батчи без поля считаются `rank`.

### T06. Алгоритмы

Все движки чистые и детерминированные: состояние выводится из участников (в порядке загрузки),
лога пар, корзин и настроек.

- **merge, swiss, round_robin** — без изменения логики. Переносятся на Engine v2.
- **insertion** — k-ичная вставка в порядке загрузки. Для новичка x окно позиций `[lo, hi)`
  в текущем списке L сначала сужается известными прямыми ответами x против L[lo..hi).
  Ничья означает «x ниже». Противоречие (нетранзитивность) решается в пользу ближайшей победы x.
  Если окно не сошлось, спрашивается `rank` из x и до k−1 равномерно расставленных опор.
  `plannedScreens` = Σ ⌈log_k(i+1)⌉.
  Экспортируется общий `insertionStep(base, pending, log, k)`: его же использует добавление
  в готовый сегмент (T08).
- **top_k** (`{k: K}`):
  - Сначала вставкой строится L из первых K участников.
  - Дальше идёт отсев. Порог t = L[K−1]. Кандидат выбывает, если прямо проиграл (или сыграл
    вничью) порогу либо любому ранее вытесненному из L. Вытесненные ниже всех в L,
    поэтому по цепочке он ниже K участников.
  - Если у первого нерешённого кандидата нет ответа против t, спрашивается `pick` из t
    и до k−1 нерешённых кандидатов.
  - Выбран t — выбыли все на экране. Выбран кандидат — он обогнал t, встаёт в L вставкой
    в окне [0, K−1], прежний t вытесняется. Остальные кандидаты экрана ждут следующего порога.
  - Результат: placed = L, unplaced = остальные.
- **tiers** (`{tiers: string[2..7], rankTop: 0..T}`):
  - Пока у кого-то нет корзины, спрашивается `tier` первого по порядку загрузки.
  - Затем вставкой упорядочиваются корзины 0…rankTop−1 по одной.
  - Результат: placed — склейка упорядоченных верхних корзин, unplaced — остальные с номером корзины.
- **rating** (`{accuracy: "fast"|"normal"|"precise"}` → множитель 1/2/3):
  - Сила — модель Брэдли–Терри, MM-итерации (Hunter, 2004): 200 шагов либо до сходимости 1e-9.
    Фантомный соперник силы 1 даёт каждому одну виртуальную ничью, иначе у непобеждённых
    сила уходит в бесконечность.
  - Цель — `min(n−1, m·⌈log₂n⌉) + bonus` разных соперников.
  - Сид выбирается как у швейцарки, только вместо очков — сила. Группа добирается
    не встречавшимися с ней участниками, ближайшими по силе.
  - Результат — по силе, затем личная встреча, победы, порядок загрузки.
    `score = round(1500 + 400·log10 p)`, «как Эло».
  - «Ещё раунд» работает как у швейцарки.
- **bracket** (`{thirdPlace: boolean}`):
  - Раунд r делит участников раунда на ⌈m/k⌉ групп подряд, размеры групп отличаются не больше чем на 1.
  - Победитель группы — тот, кто прямо обыграл всех в ней, иначе спрашивается `pick`.
    Одиночка проходит без игры.
  - Финал (m ≤ k) — `rank`: места по очкам внутри финала, затем по порядку загрузки.
  - `thirdPlace` при k=2 и двух полуфиналистах-проигравших даёт пару за 3-е место.
  - Остальные — unplaced со `stage` = номер раунда вылета.
- **Решение:** как выше. Оценки экранов — `plannedScreens` каждого движка. Их сверяет
  симуляция (T19).

### T07. Исключение

- Активные участники движка — `excluded = false`. Ответы с исключённым остаются в базе,
  но движок их не видит: срез фильтрует пары по активным ID.
- Исключение в готовом сегменте удаляет строку `Ranking` участника и перенумеровывает
  места подряд. Ручной порядок остальных не меняется.
- Возврат в готовый сегмент идёт через вставку (T08).
- **Решение:** как выше.

### T08. Добавление и возврат в готовый сегмент

- Для схем со строгим порядком (merge, swiss, round_robin, insertion, rating, top_k):
  - сервис кладёт в `TournamentSegment.insertBase String?` (JSON) текущий порядок `Ranking`;
  - сегмент открывается (`in_progress`, рейтинги снимаются), и пока поле не пусто,
    вопросы задаёт `insertionStep(base, новички)`, а не схема;
  - `finalize` пишет получившийся порядок и очищает поле;
  - у top_k после вставки остаются первые K мест.
- tiers и bracket просто открываются. Ручной порядок у них сбрасывается: у корзин новичок
  получает вопрос корзины, сетка перестраивается.
- **Решение:** как выше. Так выполняется P14: старые места не двигаются, новички встают между ними.

### T09. Смена алгоритма

- `setSegmentScheme(segmentIds, scheme, settings)` меняет алгоритм.
  - Готовый сегмент открывается: рейтинги и `insertBase` снимаются. Лог остаётся.
  - «Для всех сегментов» применяет алгоритм ко всем сегментам и делает его схемой по умолчанию.
    `schemePending` снимается.
- `bonusOpponents` сохраняется.
- Размер группы ограничивается `maxGroupSize` нового движка при чтении: k турнира не переписывается.
- **Решение:** как выше.

### T10. Удаление участника

- `deleteTracks(ids, confirmReset)`. Снимаются экраны, где участник был, и legacy-пары с ним —
  та же логика, что у переноса в задаче 27. Если ответы есть, без `confirmReset` сервис
  возвращает `{requiresConfirmation, answersToReset}`.
- Файлы участника удаляются после коммита.
- **Решение:** как выше.

### T11. Импорт из Shikimori

- Новый сервис `src/server/tournament-items.ts` разрешает источники участников в файлы:
  - `{shikimori:{type,id}, title?, subtitle?, note?}`;
  - `{assetId, …}` — картинка, аудио или видео пула;
  - `{path, …}` — картинка, аудио или видео с диска;
  - файл из формы.
- Shikimori идёт пачками:
  - GraphQL по 50 даёт имя, ссылку и `poster.originalUrl`, у аниме ещё год, студии и вид;
  - картинки качаются через общую очередь `asset`;
  - запасной путь — legacy `/system/<type>s/original/<id>.jpg`.
- Подзаголовок по умолчанию:
  - у аниме — «год · студия»;
  - у персонажа — самый ранний тайтл из `characterProfile`, но только если таких
    в вызове ≤ 20. Иначе пусто: агенту рецепт велит передавать подзаголовок (P25).
- Частичный успех (P11):
  - сбой конкретного Shikimori-участника (нет постера, 404, сеть) уходит в `skipped[]` с кодом;
  - структурные ошибки отклоняют весь вызов: чужой пул, путь вне allowlist, квота,
    повтор, ни одного участника.
- **Решение:** как выше. Сайт использует тот же сервис.

### T12. Миниатюры и темп экрана

- `GET /api/tracks/:id/cover?size=thumb` отдаёт JPEG 480px.
  - Миниатюра делается ffmpeg один раз и кешируется:
    `storage/tournaments/<tid>/thumbs/<trackId>-<artId|own>.jpg`.
  - GIF и файлы до 400 КБ отдаются как есть: анимация сохраняется, а смысла сжимать нет.
  - Если ffmpeg не справился, отдаётся оригинал.
- Экран сравнения при открытии загружает миниатюры всех активных участников сегмента
  через `new Image()`. Это несколько мегабайт, и любой следующий экран уже в кеше.
- Увеличение показывает оригинал.
- **Решение:** как выше. Отдельной зависимости не добавляем.

### T13. Архивы и файлы

- `extractMediaFromZip` по-прежнему отбирает аудио и видео. Только если их в архиве нет,
  берёт картинки как участников. Имя файла без расширения становится именем участника.
- `groupArchiveTracks` и `splitFolders` работают для картинок так же.
- `POST inspect` дополнительно возвращает `imageCount` и `kind` (`media|images`).
- Форма шлёт россыпь файлов теми же `file`. Не-ZIP файл — участник, вся россыпь —
  один сегмент «Файлы».
- **Решение:** как выше. Архив OST с обложками не меняется.

### T14. HTTP API

- `GET next` отдаёт:
  - `questionKind` (`rank|pick|tier`) рядом с прежним `question` — массивом DTO,
    у `tier` из одного;
  - `scheme`, `schemeSettings`, `schemeRequired`, `tiers` (названия), `itemCount`;
  - в DTO — `subtitle`, `imageUrl`, `thumbUrl`.
- `POST compare`:
  - `{ranked, rest, segmentId}` — как раньше;
  - `{pick: id, segmentId}` — выбор одного;
  - `{tier: n, itemId, segmentId}` — корзина, `n = -1` — «не участвует».
  Сервис сверяет вид и состав экрана.
- `POST [id]/scheme {segmentId, scheme, settings, allSegments}`.
- `POST [id]/tier {segmentId, itemId, tier}` — правка на доске, разрешена в любой момент.
  Если правка затрагивает упорядоченные корзины готового сегмента, сегмент открывается.
- `POST [id]/items` (multipart: `file` и JSON `sources`, `segmentId`) — добавление.
- `DELETE [id]/items {trackIds, confirmReset}` — удаление.
- `PATCH /api/tracks/:id` дополнительно принимает `subtitle`, `note`, `excluded`.
- `POST /api/tournaments` принимает россыпь файлов и `sources` (Shikimori и пул из черновика
  формы). `scheme` больше не обязателен: без него турнир создаётся с `schemePending`.
- `GET /api/shikimori/characters?animeId&role` — персонажи тайтла для формы.
- **Решение:** как выше. Старые клиенты (`scripts/e2e-run.mjs`) работают на `rank`.
  Сам скрипт учит `pick` и `tier`.

### T15. MCP

- `tournament_create`:
  - `scheme` необязателен, без него турнир создаётся с `schemePending` (P15);
  - сегмент принимает `items` (прежнее `tracks` остаётся синонимом) в любой форме T11;
  - ответ дополнительно содержит `itemCount` и `skipped[]`.
- Новые инструменты:
  - `tournament_items_add {id, segmentId?, segmentTitle?, items}`;
  - `tournament_items_update {id, items:[{trackId, title?, subtitle?, note?, excluded?, coverArtId?}]}`;
  - `tournament_items_remove {id, trackIds, confirmReset?}`.
- Ответов, корзин, мест и выбора алгоритма у агента нет. Алгоритм — только через `scheme`
  при создании, по прямой просьбе человека.
- Рецепт сборки базы (P25) — в описании `tournament_create` и в гиде
  [sdk-guide.md](sdk-guide.md). В инструкцию `initialize` (≤3 КБ) — одна строка.
- Инструментов становится 64. Обновляются списки имён и тесты.
- **Решение:** как выше.

### T16. SDK

- `Participant` получает `subtitle?`, `tier?` (название корзины), `link?` и `kind?`
  (`audio|video|image`). Новые текстовые источники — `participant.subtitle` и `participant.tier`.
- `reconcileSource`:
  - эти поля авторитетны из турнира;
  - у картинки нет звука, визуал — привязка cover (T01);
  - в участники идут только строки `Ranking` — участники со строгим местом.
- `video_source_list` показывает у сегментов и турниров `kinds`: какие виды участников есть.
- Новый полный пример `video_examples` `top-images`: ручной топ, участники только с картинкой,
  подзаголовок и музыка документа.
- Топ по картинкам без звука проверяется живым кадром и звуком (QG).
- **Решение:** как выше. Корзины без мест агент берёт из `tournament_get` и привязками `track`
  в собственном документе (доска `board.*`).

### T17. Сайт

- Форма создания: название, слепой режим и источники-вкладки «Файлы и архивы · Пул · Shikimori».
  Shikimori и пул копятся в черновике с превью и удалением, галочка «каждый тайтл — свой сегмент».
  Алгоритма в форме нет.
- Страница турнира:
  - вкладки сегментов как сейчас;
  - блок «Алгоритм» с окном выбора: описания, настройки, размер группы, оценка экранов
    для текущего числа участников, «Для всех сегментов»;
  - «Состав» — сетка карточек с исключением, удалением, добавлением и правкой подписей;
  - редактор разбивки, как был, показывает превью картинок.
- Экран сравнения:
  - вопросы `rank`, `pick`, `tier`;
  - карточки картинок с увеличением (лупа, стрелки, Esc);
  - предзагрузка миниатюр;
  - звук — прежний `MediaPlayer`;
  - если алгоритм не выбран — окно выбора.
- Результаты: миниатюры, «без мест» свёрнуто с причиной (не вошли, вылет в раунде N, корзина),
  доска корзин с перетаскиванием.
- **Решение:** как выше.

### T18. Бюджеты

- Картинки — в `maxArchiveBytes`. Файл картинки не больше 32 МБ.
- Участников в турнире не больше 2000: это технический бюджет движков (BT и вставка на 2000 — миллисекунды).
- За один вызов MCP — не больше 300 Shikimori-участников. Около 75 секунд уходит на картинки,
  остальное агент добавляет следующим вызовом.
- **Решение:** как выше.

### T19. Проверка алгоритмов

- Симуляционный набор `engines/simulation.test.ts` на детерминированном PRNG.
  - Скрытый транзитивный порядок, оракул отвечает по нему на любой вид вопроса.
  - N ∈ {2, 3, 5, 8, 13, 30, 60}, k ∈ {2, 3, 5, 7}.
- Проверяется:
  - завершение;
  - число экранов ≤ `plannedScreens`, кроме оценок-моделей, у них отдельный допуск;
  - точный порядок у merge, round_robin, insertion, tiers с упорядоченными корзинами;
  - точный топ-K у top_k;
  - точный финал у bracket;
  - корреляция Спирмена ≥ 0.85 у swiss и rating (на «обычно»);
  - смена алгоритма посреди прогона не теряет ответы и доводит до конца.
- Отдельно — шумный оракул (10% ответов наоборот): движки завершаются и не зацикливаются.
- **Решение:** как выше.

## Риски

- Переписывание интерфейса движков задевает все вызовы. Страховка — старые тесты
  с прежними утверждениями и симуляция.
- `next` вызывается на каждом экране и переигрывает лог. BT на 2000 участников ×
  тысячи пар — миллисекунды, вставка — O(n·log n) поисков по логу. `lookup` линейный,
  поэтому движки строят индекс пар один раз на вызов.
- Схема Prisma меняется, а dev-сервер, worker и MCP держат старый клиент.
  После `db:push` их нужно перезапустить.
