# MCP: ручные топы

Реализовано 2026-09-04. ИИ может собрать ручной топ из медиапула и вернуть
готовый конструктор для проверки и запуска рендера пользователем.

- `create_top_project({title})` возвращает `projectId` и `/projects/<id>`.
- `set_top_items({projectId, items, clipSec?, order?, introText?, outroText?})`
  **заменяет весь список** одной транзакцией. `items` идут от #1 (лучшего) к #N.
  Элемент: `{audioArtId, artId?, customLabel?}`. Аудио и фон должны принадлежать
  актору; звук обязателен у аудиоисточника, фон — картинка или видео.
  Разрешены 1–200 уникальных аудиоисточников. Некорректный ввод сохраняет старый топ.
  `clipSec` по умолчанию 30, `order` — `desc` (N→1), режим — `active_snippet`.
  Пустой текст интро/аутро выключает соответствующий экран.
- `get_project` для топа возвращает реальные позиции RenderConfig, рассчитанные
  по RMS фрагменты, временные позиции, длительность, `readyToRender`, `warnings`
  и `renderAllowed`. Первый вызов может занять минуты: увеличьте таймаут клиента.
  Отсутствующие файлы и нерассчитанные фрагменты не скрываются.

Все операции используют существующего MCP-актора и сервисный слой, создание
и заполнение требуют `tournament:create`. Рендер не экспонируется через MCP.
Схема БД и существующие проекты не меняются.

Проверка: `npx vitest run src/integration/mcp-top.integration.test.ts` —
настоящий stdio-клиент, расчёт активного окна, порядок N→1, изоляция владельцев,
атомарность при ошибке и отсутствующий файл.

## Данные для карты предпочтений

- `shikimori_user_favourites` сохраняет также `people` и `seiyuu`, чтобы явно
  избранные музыканты не терялись за персонажами.
- `shikimori_person({id})` возвращает имя, сайт и участие в аниме с ролью.
- `shikimori_character` включает исходное `description` (возможны BBCode и спойлеры).
- `shikimori_user_history({user,page?,limit?})` возвращает страницу публичной
  истории и `nextPage`; дополнительная запись API для проверки следующей
  страницы не выдаётся дважды. Максимальный размер страницы — 100.
- Таймаут HTTP начинается после ожидания лимита API. Длинная очередь не
  расходует время сетевого запроса до его отправки.

Проверки: `src/integration/shikimori.integration.test.ts` (избранные исполнители,
роли, описания, пагинация) и `src/lib/shikimori-queue.test.ts` (очередь >80 запросов).
