# feature — стадии задачи

Проект личный: правки вносит только владелец, поэтому процесс лёгкий.
Каждая стадия — файл в папке задачи и коммит в её ветке.
Гейты — это явные ответы владельца в чате. Без такого ответа на следующую
стадию не переходим. Исключение одно — [автономный режим](#автономный-режим).

## Где состояние

- Папка задачи: `.ai/features/NN-slug/`. `slug` — короткий, латиницей, kebab-case.
- Номер `NN` выбирай так, чтобы не пересечься с невлитыми задачами. Их папки лежат
  только в их ветках. `NN` = max(21, номера папок в `.ai/features/` на `main`, номера
  из имён веток `git branch --list 'feat/*' 'fix/*' 'chore/*'`) + 1.
- Статус задачи хранится во frontmatter её `README.md`: `track`, `stage`, `branch`, `pr`.
  Любая новая сессия начинает с него.
- **Каждый коммит стадии сдвигает `stage` на следующую** и отмечает чекбокс в `README.md`:
  - бриф → `product` или `tech`;
  - продукт → `tech`;
  - техника → `plan`;
  - план → `build`;
  - PR → `review`;
  - перед merge → `merged`.

  Иначе следующая сессия начнёт задачу заново.
- Шаблоны файлов лежат в [`templates/`](templates/) рядом с этим файлом.
- Стадии по порядку: `brief → product → tech → plan → build → review → merged`.

## Автономный режим

Владелец может явно разрешить агенту пройти задачу без него: «делай автономно»,
«автономно до вливания» и подобное. Тогда:

- Гейты «продукт ок», «техника ок» и «принято» пропускаются. Решение по каждой развилке
  агент принимает сам и записывает в `product.md` или `tech.md` так же, как решения владельца.
- Дословные слова разрешения записываются в `brief.md`, а в `README.md` задачи — пометка
  «автономный режим».
- QG по `verify` и свежее ревью остаются обязательными. Красный QG или неисправленное
  существенное замечание ревью останавливает вливание. Агент сообщает об этом владельцу
  и сам не вливает.
- После зелёного QG и ревью агент делает стадии 5–6 без ожидания: PR, `stage: merged`, merge в `main`.
- Разрешение действует только на задачу, в которой дано. Следующая задача снова идёт по гейтам,
  если владелец не написал об автономности заново.
- Вопрос, который нельзя решить из кода, документов и брифа, — например выбор продукта,
  который владелец явно оставил за собой, — всё равно задаётся владельцу.

Без явного разрешения автономного режима нет. Агент не выводит его из тона,
спешки или фраз вроде «сделай побыстрее».

## Треки

| Трек | Когда | Стадии |
|---|---|---|
| `product` | Меняется то, что видит или делает пользователь | все |
| `tech` | Рефакторинг, инфраструктура, надёжность, поведение не меняется | без `product` |
| мелочь | Опечатка, однострочный фикс, правка доки | без папки задачи: ветка → правка → QG → PR |

Трек выбираешь ты и объясняешь выбор одной фразой. Владелец может его поменять.

## Вызовы

- `/feature` (`$feature` в Codex) без аргументов — покажи невлитые задачи, текущую ветку
  и следующий шаг. Невлитые задачи — это ветки `feat/*`, `fix/*`, `chore/*`. Статус каждой
  читается без переключения: `git show <ветка>:.ai/features/<NN-slug>/README.md`.
  Если задача одна, предложи продолжить её.
- `/feature <бриф>` или бриф обычным текстом — начни стадию 0.
- Ответы владельца на гейтах («продукт ок», «техника ок», «принято», «вливай») переводят задачу дальше.

## Стадия 0 — бриф

1. Рабочее дерево должно быть чистым. Выполни `git switch main && git pull --ff-only`,
   затем `git switch -c <тип>/NN-slug`. Тип ветки: `feat` для продукта, `fix` или `chore` для техники.
2. Создай папку задачи из шаблонов `README.md` и `brief.md`.
3. Слова владельца запиши в `brief.md` дословно. Уточняй по одному-два вопроса за раз,
   ответы записывай туда же. Не додумывай за владельца: свою догадку помечай как догадку.
4. Выбери трек и запиши в «Успех», как поймём, что задача сделана.
5. Коммит `docs(NN): brief`. Дальше стадия `product` или `tech`.

## Стадия 1 — продукт (только трек `product`)

- Обсуди, что и для кого делаем: сценарии, не-цели, что сделает результат провалом,
  даже если он формально работает.
- Каждое решение оформи как `P01…`: вопрос → варианты → рекомендация → **решение владельца**.
  Вопросы задавай партиями, рекомендацию ставь первой.
- Если доступен `superpowers:brainstorming`, им можно вести разговор,
  но результат всё равно пишется в `product.md`, а не в `docs/superpowers/`.
- Гейт — «продукт ок». После него коммит `docs(NN): product decisions`.

## Стадия 2 — техника

- Сначала прочитай карточки затронутых зон в [`.ai/map/`](../../../.ai/map/) и проверь
  код. В `tech.md` раздел «Исходная система» описывает только то, что ты реально видел в коде.
- Решения оформи как `T01…` в том же формате. Если опираешься на внешние библиотеки или API,
  сверяйся с их документацией, а не с памятью.
- Перечисли зоны, которые меняются: по ним потом обновляются карточки.
- Гейт — «техника ок». После него коммит `docs(NN): tech decisions`.

## Стадия 3 — план

- План пишешь сам в `plan.md`: задачи с чекбоксами, у каждой файлы, тесты и критерий «готово».
- Последняя задача всегда «Знания»: обновить карточки `.ai/map/` затронутых зон, а при
  необходимости и `AGENTS.md`.
- **Гейта нет.** Сделай коммит `docs(NN): plan`, коротко покажи план и сразу
  переходи к реализации. Владелец может остановить.
- Если доступен `superpowers:writing-plans`, можно опираться на него, но план живёт в `plan.md`.

## Стадия 4 — реализация и QG

1. Иди по задачам плана. Новое поведение пиши через TDD: сначала красный тест.
   Отмечай чекбоксы. Коммить по задачам в conventional-стиле на английском,
   как в истории репозитория: `feat(studio): …`.
2. Пройди QG по скиллу [`verify`](../verify/SKILL.md): обязательная тройка плюс живые проверки
   по затронутым зонам. Результаты с цифрами и путями к доказательствам запиши в `verify.md`.
3. Ревью: дай дифф ветки свежему ревьюеру. Подойдёт субагент, `/code-review`
   или `superpowers:requesting-code-review`. Существенное исправь, остальное
   с причиной запиши в `verify.md`.
4. Заполни в `verify.md` раздел «Что посмотреть руками»: страницы, ролики, кадры, команды.
5. `git push -u origin <ветка>` и `gh pr create`. Заголовок PR — `NN: <название>`, в теле:
   ссылка на папку задачи, что сделано, итоги QG и что посмотреть руками.
6. В `README.md` задачи поставь `pr` и `stage: review`, затем коммит и push.

## Стадия 5 — проверка владельцем

- Дай ссылку на PR и чек-лист «Что посмотреть руками».
- Замечания исправляй в той же ветке и дописывай в `verify.md` → «Замечания владельца».
  После исправлений снова прогоняй QG.
- Гейт — «принято» или «вливай».

## Стадия 6 — вливание

1. Проверь, что карточки `.ai/map/` соответствуют коду ветки.
2. Добавь строку задачи в [`.ai/history.md`](../../../.ai/history.md). В `README.md` задачи
   поставь `stage: merged` и дату в `merged`. Коммит `docs(NN): merged`, затем push.
3. `gh pr merge <pr> --merge --delete-branch`, потом `git switch main && git pull --ff-only`.
4. **Без явного «принято» или «вливай» владельца не вливать никогда.** Единственное
   исключение — [автономный режим](#автономный-режим), разрешённый владельцем для этой задачи.

## Мелочь

Ветка `fix/<slug>` или `chore/<slug>` без номера и без папки задачи. Дальше правка,
QG по `verify` (для чистых доков достаточно проверить ссылки), PR, «принято», merge.
Строку в `history.md` не добавляем.

## Попутные находки

- Если находка связана с задачей и небольшая, чини её в задаче и отметь в `verify.md`.
- Остальное записывай в `README.md` задачи → «Хвосты» и сообщай владельцу.
  Сам ничего нового не заводи.

## Правила

- Документы задач пиши по-русски, код и коммиты — по-английски.
- Ворктри по умолчанию не используй: в новой копии нет `.env`, `storage/`, `prisma/dev.db`
  и `node_modules`, а dev-сервер будет конфликтовать за порт 3000.
  Работай в основном чекауте.
- Перед `npm run dev` проверь порт 3000. Подробности в [`dev-env.md`](../../../.ai/map/dev-env.md).
- Каждая стадия должна быть закоммичена. Задача, у которой половина состояния
  только в чате, для следующей сессии потеряна.
